## Repository Restructure - Separating Public and Proprietary Content

### The Problem

After setting up the initial repository and downloading the first 5 MIT course reading PDFs, we discovered that these PDFs contain proprietary MIT content (excerpts + talking points) that shouldn't be pushed to the public GitHub repository.

The git history showed:
- Commit fa50b30: "Initial project" - clean, already on GitHub
- Commit 966ff30: "Add readings" - contained 5 PDFs, TODO.md, PLAN.md, updates to CLAUDE.md and docs/reading.md

### Solutions Explored

We considered several approaches:

#### 1. Two Remotes with Separate Branches
- Remote "github" for public content (branch `__main__`)
- Remote "localmam" (local bare repo) for private content with PDFs (branch `__mit__`)
- **Problem:** Would require constantly working on one branch and cherry-picking to the other
- **Complexity:** High - manual synchronization between branches

#### 2. Git Submodules
- Main repo for public content
- Separate submodule repo for readings/
- **Problem:** Adds complexity for what's essentially "download once, keep readonly" content
- **YAGNI:** Version control on PDFs not really needed

#### 3. Git Worktrees
- Multiple checkouts of same repo in different directories
- `/opt/clones/github/.../MindsAndMachines` on `__main__` (no readings/)
- `/opt/clones/local/...` on `__mit__` (with readings/)
- **Problem:** Doesn't solve the fundamental issue of needing readings/ present during daily work

### Final Solution: KISS Approach

**Keep It Simple:**
- Single repository, single branch (`__main__`)
- Add `readings/` to `.gitignore`
- PDFs exist locally but are never committed or pushed to GitHub
- No version control on PDFs (they're static downloads anyway)

**Benefits:**
- Simple to understand and maintain
- No complex git gymnastics required
- Readings physically present for study
- GitHub repo stays clean and public-friendly

### Key Decisions

1. **No version control on readings PDFs**
   - They're static course materials
   - YAGNI principle applies
   - Simplifies git workflow dramatically

2. **Single branch workflow**
   - All work happened on `__main__`
   - No manual synchronization needed
   - Gitignore handles the separation

3. **KISS over complexity**
   - Rejected more complex solutions (multiple remotes, submodules, worktrees)
   - Chose simplest approach that meets requirements
   - Easier to maintain and understand

### Lessons Learned

1. **Think before committing proprietary content**
   - Should have checked MIT's terms before adding PDFs to git
   - .gitignore should be set up early

2. **KISS usually wins**
   - First instinct was complex (two remotes, branches, etc.)
   - Stepping back and questioning assumptions led to simpler solution

3. **Git is flexible**
   - Multiple ways to solve the same problem
   - Important to understand trade-offs of each approach
   - Sometimes the simplest solution isn't a "git trick" at all
